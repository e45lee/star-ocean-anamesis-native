# Game server API catalogue

Every API the STAR OCEAN: anamnesis client can call on its game server, as far as the client code shows. It's the reference for the local server (`server/`, see `docs/history/PLAN-restore-original.md`) and for `docs/server-rules.md`, which holds the game rules each API needs.

Written 2026-09-29 by agent `apicat`. **Generated in part:** the FunctionIDs, method and wire signatures, caller lists and status lines come from scripts over both builds; the request meanings, response keys, effects and tables are hand-written from the sources below. Where a meaning is inferred rather than read from code, the entry says so ("as far as the call sites show", "likely").

## Sources
- **How the real server worked** (transport, wire format, encryption, session and bridge handshake, downloads, multiplayer): [online-server.md](online-server.md).
- **Methods and FunctionIDs:** `NetworkApiCaller::<Api>` (first read in the offline build, whose API layer is the same as 3.7.0's; decompiled in `work/decomp/apicat-netapi*.resolved.c`). Each method passes its FunctionID to `CErrorHandlerWrap::SetRetry` and `DisconnectDialog`; the variadic front ends (`ItemCompose(u64, u32 n, ...)` and friends) forward to their `*Array` twins.
- **Wire signatures:** `Aska::Yayoi::GameRPC::Cli::GameProtocolProxy::Send<Api>(RequestHeader const&, ...)`. The protocol is positional and typed (no key names), serialised by `GameProtocoledData::Set<Api>` and encrypted with `Aska::Cryption::Ninja`. Arrays go as (pointer, count) in the signature and as count + elements on the wire. The byte layout of every request and its reply FunctionID are in each entry's **Wire** line and in [Wire format](#wire-format) (generated by `tools/api_wire.py` from the `wire/` selftest). Some methods send more than the `IApiCaller` signature shows, e.g. `MissionEnd` adds the serialized battle log.
- **Callers:** a scan of `work/libSOA-3.7.0.so` (and of the offline build, which adds none) for code that materialises each FunctionID constant (`movz`/`movk`), i.e. the screens that issue the request and then poll `IsRequesting(fid)` / `IsSuccess(fid)`. Hits inside unexported static functions (lambdas, `CAppState` state tables) are attributed to the nearest exported symbol and shown as "unnamed code near `CClass`". A request issued without its fid constant in the same function would be missed.
- **Responses:** `CApiNotify::On<Api>Res` → `DeserializeToInfo` → `CParameterManager::Deserialize` (docs/notes.md, "API response handling (CApiNotify)"). The key schema is `port/fakeapi/schema.txt` (the `--fake-server-schema` dump) and the element fields `port/fakeapi/fields.txt`.
- **Which response keys belong to which API** is not in the handler: every handler parses the whole `data` map generically. The keys listed per API are the ones its handler's post-apply steps and its screens consume, matched by the info names and the handler code in `port/src/native/api/api_notify.cpp`. For the handlers with inline code the keys are pinned: the `CParameterManager` offsets each one reads were mapped to the `data` children with the live `infos:` dump. Treat the lists as the minimum to send.
- **Offline behaviour:** the profiles in `work/profile/*/coverage.tsv`.
- **The offline build:** its API layer is the same as 3.7.0's (only `NetworkApiCaller::BeginBridge` changed size); it removed the way into the screens, not the requests. The comparison, and this catalogue's first status labels (by build), are history: [`docs/history/libsoa-3.7.0-vs-3.8.0.md`](history/libsoa-3.7.0-vs-3.8.0.md).

## Request and response basics
- **One request at a time.** `NetworkApiCaller` has one request slot (+0xcc0 fid, 0x7b1a9377 = none). Screens poll `IsRequesting(fid)`, `IsSuccess(fid)` and `ErrorCode(fid)` (`CApiCaller` vtable +0x6a8..+0x6c0). Error codes such as 0x2c93 / 0x2c96 are checked by callers (e.g. `CStageManager` on MissionEnd).
- **Retry.** Every method registers a retry closure (`CErrorHandlerWrap::SetRetry(fid, fn)`) that re-issues the same request; a disconnect shows `DisconnectDialog(-0x3b3, fid)`.
- **Response envelope:** a msgpack map `{"data": {<InfoName>: ...}, "status": <uint>}`, plus top-level parameter sets (`Player`, `master_*` ...) when present. `DeserializeToInfo` first **clears every per-response result container**, so a response only needs the keys that changed; the owned lists (`Character`, `Item`, `StockItem`, ...) are **replaced** when sent, so send them whole or not at all.
- **`data.Time`** (a `YYYY-MM-DD HH:MM:SS` string) in any response sets the client's server-time offset when it differs from the local clock by 60 s or more (`CServerTime::UpdateServerTimeOffset`, run by every `DeserializeToInfo`). The offline build ignored the offset while `master_global.service_stop_day` existed (docs/server-rules.md, conventions).
- **Shapes:** list infos take msgpack arrays of element maps; map infos (`AddCharacter`, `MissionResultCharacter`, `LimitBreakCharacter`, `...Map`) take a map keyed by the id, **as a string** (our server) or as a uint; an array is ignored ([ason.md](ason.md#id-keyed-maps)).
- **Common post-apply steps:** `AddItem` (new items `AddItem` → owned items), `AddCharacter` (new characters `AddCharacter` → roster, no duplicate check), the limit-break sync (`LimitBreakCharacter` → owned characters' count and level cap), `UpdateStackItem` (`UpdateStockItem` / `HostPlayer.UpdateStockItem` deltas → owned stack items; count 0 erases), `AddPresentBox` (`AddPresent`).
- **Player fields** (`data.Player`, CPlayerInfo): id, name, level, exp, stamina, stamina_max, stamina_update (timestamp of the last stamina change), stamina_max_time, fol, party_id, tutorial_status, view_status(2), item_stock, gear_stock, storage_stock, follow_max, title, mascot_id, home_pc_id, support_pc_id, world_map_progress(_ep3), is_rookie, is_3d_home, inquiry_rank/point, vip_point, kiyaku_version, created_at, last_login_at, time_saving_use_count, tower_try_count, sphere211_revive_count, favor_bonus_received_at, stamina_update_by_favor. The wallet is `data.Wallet` (free_coin, pay_coin, total_coin, android_coin).

## Wire format
How a request and its reply look as bytes. The transport, the encryption and the session are described in [online-server.md](online-server.md) (sections 2–4); this section is the byte layout.

**How we know.** Most of this was measured, not just read, by running the client's own serializers in the selftest `wire/` (`port/src/native/api/wire_test.cpp`):
- `wire/request-layouts` calls all 193 request serializers `GameProtocoledData::Set<Name>` with distinctive arguments and captures the plaintext body. It uses a stand-in session key that is empty, so the encrypt step fails before it touches the laid-out plaintext. Every body matches the rules below, and the 3.7.0 code produces identical bytes.
- `wire/reply-roundtrip` builds a reply with the client's code, seals it with `GameProtocol::Serialize` and reads it back with the client's receiver.
- `wire/battle-log`, `wire/deco-payload` and `wire/ason-roundtrip` produce the MessagePack examples in [ason.md](ason.md).
- `tools/api_wire.py` reads the FunctionIDs out of the serializers and writes the per-API **Wire** lines in the entries below. The measured layouts are in [`api-wire.txt`](api-wire.txt).

Labels used here:
- **[run]**: bytes produced by running the client code in the selftest;
- **[code]**: read from the decompiled code;
- **[illustrative]**: made by hand from the rules;
- **[unknown]**: not recoverable from the client.

### Packet
```
 offset  size  field
 +0      24    header, scrambled (below)
 +24     n     body: plaintext, or the Ninja envelope of the plaintext when flags & 0x80
 +24+n   20    SHA-1 of bytes [0, 24+n)   (GameProtocol::Serialize appends it; the receiver checks it)
```
- **Header.** The 16 logical bytes are:
  ```
  u32 size      24 + n: the SHA-1 trailer is NOT counted
  u32 fid       the FunctionID of this message
  u32 counter   copied from GameProtocoledData+0x34 (set by the peer; not traced) [code]
  u8  flags     0x80 = body encrypted; 0 for the clear messages
  u8[3] 0
  ```
  All little-endian. **[run]**
- **Scramble.** Take t = `clock_gettime(CLOCK_MONOTONIC)` in nanoseconds, as a u64.
  - Wire bytes 0..7 are t's bytes 6, 4, 3, 0, 7, 1, 2, 5.
  - Wire bytes 8..23 are the logical bytes, with byte i XORed with t's byte (i & 7).
  - The receiver (`GameProtocoledData::Deserialize`) rebuilds t from bytes 0..7 and un-XORs the fields. It then:
    1. reads size + 20 bytes;
    2. checks the SHA-1 and rejects a mismatch with **-0x3b8**;
    3. rejects a FunctionID it doesn't know, also with -0x3b8.
  - **[run]**: `wire/reply-roundtrip` round-trips a packet, and a corrupted trailer is refused.
- **Encryption.** Every message except 12 has flags 0x80. Its body is the plaintext wrapped in the Square Enix "Ninja" envelope under the session key: magic 0xABBAABBA, a 24-byte header and a 32-byte trailer ([online-server.md "Encryption"](online-server.md#encryption-ninja): ten block ciphers, all reproduced in `server/net/ninja/` and checked against the client).
  - The requests sent in the clear are StartBridge, NoLoginStart and UpdateSession.
  - The encrypted plaintext is laid out first, at the tail of the buffer. The helper then writes the envelope from +24, with room for `((len + 0x98) & ~0x7f) | 0x20` plus 0x20 bytes.

Example **[run]**: a clear reply packet (NoLoginStartRes) carrying `{"data": {"Time": "2021-06-30 12:00:00"}, "status": 0}`, 88 bytes.
```
00 3d cc 15 00 3f f1 0d  51 3f f1 cc d9 d9 da a8 14 3f ab 96 3d 0d 00 00   header: t = 0x00000d3dccf13f15 ->
                                                                           size 68, fid a8dad4e4 (NoLoginStartRes),
                                                                           counter 5a5a0001, flags 0
28 00 00 00                                                                u32 length 40
82 a4 64 61 74 61 81 a4 54 69 6d 65 b3 32 30 32 31 2d ... a6 73 74 61 74 75 73 00   MessagePack (40 bytes)
f5 2e 51 1d 22 7c 05 16 98 bc bb 04 2a fb 6d 7a ef de ea c1                SHA-1
```

### Request body
The plaintext is the **RequestHeader** followed by the method's arguments, **in declaration order, packed with no alignment padding, little-endian**. It's a custom positional binary format, not MessagePack. **[run: all 193 requests]**

| Wire type (serializer parameter) | Encoding | Example |
|---|---|---|
| `RequestHeader const&` | 16 bytes: u32 player id, u32 second value (`CParameterPlayer` +0x68, meaning not pinned), u32 request id (`CHash32("%u_%u_%llu_%u", …)`, kept on a retry), u16 (never written by `PresendApiCall`, so 0) **[unknown]**, u16 asset revision (`version.bin` `revision`) | all requests |
| `unsigned char` / `signed char` | 1 byte | `Home3DAnd2DSwitching`, Login's flag |
| `unsigned int` / `int` | 4 bytes | ids, counts, mission type |
| `float` | 4 bytes IEEE-754 | latitude / longitude of `LocationRegist`, `NeighborRegist`, `NeighborList` |
| `DeviceType` | u32 (2 = Android); the serializer refuses > 99 | `NoLoginStart`, `CreatePlayer` |
| `unsigned long` | 8 bytes | uids (characters, items) |
| `T const* p, unsigned int n` (T = u64 or u32) | **u32 n first**, then n × T. The count comes before the data although it follows the pointer in the signature | `LockItem`, `DeepSpaceMissionStart` |
| `signed char const* p, unsigned int len` | u32 len, then len bytes | Login's tokens, the MissionEnd battle log, `SetCharacterDeco` |
| `signed char const*` with no length | a **fixed-width field**: `memcpy` of N bytes from the pointer. N depends on the API: 36 (UUID), 33 (gacha hash: 32 hex + NUL), 32, 16, 8, 128 (`SendErrorLog`), 191 (names, config text) | `UpdateName` char[191], `GachaOnce` char[33] |

- **Fixed-width fields are not zero-padded.** The serializer copies N bytes whatever the string's length, so the bytes after the NUL are whatever follows the source string in memory. A server must read up to the first NUL. **[code, run]**
- **Argument checks** in the serializers (they return **-0x3bd** and nothing is sent) **[code, run]**:
  - an empty or NULL fixed string (Login, CreatePlayer, UpdateName, …);
  - `DeviceType` > 99;
  - `UpdateParty` party index ≥ 7;
  - mission type ≥ 4, compared unsigned, in `MissionStart`, `GetMissionList`, `MissionTalk`, `EndMissionTalk` and `MissionFailed`. So a type of 0xffffffff, which the port's `mission:` route passes, would never reach a real server;
  - `BoostCharacter` / `AddStatusCharacter` count ≥ 10000;
  - `SellStackItem` count outside 1..999;
  - `UseHealItem` / `UseFavorItem` count outside 1..9999.
  - The per-API lines mark these "range-checks an argument".
- **FunctionIDs.** Every request and every reply has its own FunctionID. The reply of `<Name>` is `<Name>Res`, except Login → LoginResult, SimpleLogin → SimpleLoginResult, StartBridge → ResultStart and UpdateSession → ResultUpdateSession. Each entry's **Wire** line gives both. The ids are unrelated hashes: GetPlayer `9a056905` → GetPlayerRes `111cebbc`. **[code]**
- The IApiCaller method's arguments aren't always the wire arguments. The method may add some (MissionEnd's battle log, DeviceType, …) or turn a `vector` into (pointer, count). The **Wire** line is the wire side.

### Reply body
- **Normal replies** (`<Name>Res`): after decryption, **u32 length + that many bytes of MessagePack**. **[code]** for the encrypted ones (`Get<Name>Res`); **[run]** for the clear `NoLoginStartRes`.
- **`LoginResult` / `SimpleLoginResult`**: u32 fid + u32 length + MessagePack.
- **`ProtocolError`** (fid `05aed673`, clear): s64 `Aska::Status` + u32 failing FunctionID ([online-server.md "Errors and status codes"](online-server.md#errors-and-status-codes)).
- **Clear specials**: `MaintenanceRes` (u32 mode + blob), `PartialMaintenanceRes` (u32 + blob), `AccountSuspendedRes` (u8 + blob), `ResultStart` (three fixed-width strings: `char[1024]` token, `char[128]` bridge URL, `char[8]`, 1160 bytes; **[run]**: measured on `SetResultStart`, and `GetResultStart` reads soa-server's), `ResultUpdateSession` (empty).
  - Two ordinary replies are also serialized in the clear: `EquipAccessoryRes` and `CoinDepositAndroidUpdateRes`.
- **The MessagePack** is the `{"data": {...}, "status": n}` map of "Request and response basics". `CApiNotify::On<Name>Res` → `DeserializeToInfo` → `ASON::DeserializeBinary` → `CParameterManager::Deserialize`, described below.

### Bodies are ASON
The MessagePack in reply bodies, and the MessagePack payloads some requests carry (the MissionEnd / MissionFailed / Sphere211 battle log, the SetCharacterDeco payload), are **ASON**, the engine's MessagePack. [ason.md](ason.md) describes it:
- the encoding and its deviations from standard MessagePack;
- the AValue object model;
- how keys reach C++ fields (CHash32) and how id-keyed maps parse their keys;
- the request-side serializer, with the full battle-log and deco key lists;
- how our `server/include/soaserver/msgpack.h` compares, with an annotated hex example.

## Player state and response lifetimes
The `data` infos live in `CParameterManager` (offsets from the live `infos:` dump of the removed drive hook, 2026-09-28: docs/history/notes-native-switches.md "API response handling"). Three kinds matter to a server:
- **Owned state**, the player's persistent data. Post-apply steps merge deltas into these, and sending the key itself **replaces** the whole list (notes: "Response shapes learned from the live check"). A full-state response (NoLoginStart offline, Login/GetPlayer online) should send them all once:

| `PartySet` | +0x1840 (map +0x1878) | party sets (PartySetInfo) |
| `Wallet` | +0x1f20 | coins |
| `PresentBox` | +0x2048 (vector +0x2080) | present box |
| `Achievement` | +0x6790 (map +0x67c8) | active achievements |
| `BoxGachaList` / `BoxGacha` | +0x7240 / +0x7290 | box gacha progress |
| `StepUpGacha` | +0x73d0 | step-up progress |

  Other state-like keys that nothing resets: `ActiveMissionList` / `ActiveEventMissionList` / `ActiveTowerMissionList` / `ActiveWorldMapMissionList`, `LoginBonus`, `PremiumLoginBonus`, `CampaignInfo`, `GachaHashMap`, `GachaCount` / `SaleGachaCount` / `GachaDayLimitCountInfo`, `ExchangeShopExCount`, `TitleList`, `StampList` / `StampSlot`, `ConfigInfoList`, `PlayMission`, the Sphere211 and deep-space infos.
- **Per-response results**, reset by `DeserializeToInfo` before every response is applied: `AddItem`, `AddCharacter`, `UpdateStockItem` (and `HostPlayer`), `LimitBreakCharacter` / `LimitBreakItem`, `GachaItems`, `GiftGachaItems`, `MissionResultCharacter`, `MissionResultCharacterFavor`, `add_characters_exp`, `DropList` / `RareDropList` / `CommonDropList` / `ClearPresentList`, `BattleEvaluationResultInfoList`, `BoostedCharacterResult`, `UseFavorResultInfo`, `SetAssistResult`, `UpdateBoxGacha(List)`, `UpdateStepUpGacha`, `UpdateStorageItem`, `UpdateGearList`, `AddStampList`, `AddTitleList`, `AddFollow`, `AddFriendGauge`, `ItemGetList`, `PartialMaintenance`, the Sphere211 / universe result infos. A handler that doesn't find them in the response sees them empty.
- **Everything else** (`MissionParameter`, `BattleParameter`, `MissionEndResult`, `PresentGetResult`, `ComposeResult`, `EvolutionResult`, `SellResult`, `ExchangeResult`, `EquipWeaponResult`, ...) is neither reset nor merged: it keeps the last value sent until the next response sends it again. Always send them with the API they belong to.

The split between the last two groups comes from the CParameterManager offsets `DeserializeToInfo` touches (`port/src/native/api/gen/api_notify_a2c.cpp`), so it's a strong hint, not a proof: a container reset through a pointer computed elsewhere would be missed.

## FakeApiCaller's FunctionIDs
The dormant `FakeApiCaller` (notes: "Offline server (FakeApiCaller)") registers its canned files under its own copy of the FunctionIDs, and some of them differ from `NetworkApiCaller`'s: e.g. `EquipAccessory` (fake `1f3c9eca` = EquipWeapon's), `Blacklist*` (the Follow fids), `SendErrorLog` (UpdateKiyakuVersion's), `AchievementReceiveList`, `LimitBreakCharacter_Legacy`, the ClearNew* / sale family (all `00ee45f7`). The entries below flag each such mismatch. **A local server must key its dispatch on the method, or on the `NetworkApiCaller` fid**, not on FakeApiCaller's.
