# Client changes

Every change to functionality extracted from the original game (the 3.7.0 `libSOA.so` the port runs), per the restore run's rule: keep changes in the local server emulator whenever possible (`port/PLAN.md` "Working rules", server-first).

Each entry says:
- the symbol;
- what the original (3.7.0) code does;
- what it was changed to;
- why a server-side fix wasn't possible;
- the switch that controls it.

Pure native ports that are bit-exact with the guest code are not changes and have no entry.

**Since the 3.7.0 rebase (2026-10-01; P3 + H of `port/PLAN.md`)** the client code changes are: the FakeApiCaller route of `--server inproc` (`port/src/native/api/fakeapi.cpp`: "Local-server refusals ...", the "... on the FakeApiCaller route" entries, "The battle log on the FakeApiCaller route", "`FakeApiCaller` session queries"), the notice board page (`webview_local.cpp`), the tower (`restore_tower.cpp`), the high-resolution rendering (`ui_utility.cpp`, on by default), platform370's two native patches (`service_stop_day`, the coin shop instead of the sale-stopped dialog; "Emulator mode") and, only with `--lang en`, platform370's English mode ("English mode"). The data overrides are the server's: both modes serve them in the master the client downloads from the server's CDN. The entries of the port before the rebase (the restore image, the restored login / tutorial groups, favorability, the home and menu workarounds, the server's login-bonus popup request, the story campaign's client hooks, the 3.7.0 texts insert) were deleted with their code; they are in the history of this file (tag `pre-rebase-370`) and summarised in `docs/history/client-changes-3.8.0.md`.

## Data overrides (no code change)
These change data the unmodified client code reads, as the online server's data did. They're listed because they change what the client does.

### `master_global.service_stop_day` dropped from the master the client downloads
- **Symbols affected:** the row's readers in 3.7.0, `CTitle::Setup` and `CPhase_Server::CPhase_Server` (the service-end check; 3.7.0's `CTimeUtility::NowTime` doesn't read it).
- **Change:** the master the server's CDN serves has no `service_stop_day` row (`server::apply_client_master`, both modes), as in service. The APK's built-in master still has it, so the first boot's check is taken out by platform370's patch ("Emulator mode" below).
- **Switch:** always (the served master).

### The English master and other `-en` files (`--english`)
- **Symbols affected:** `CGameResourceManager::FileExistLanguage` / `RegisteredFileLanguage` / `IsFileExistDownloadFolder` (a client with `CLanguage::Current` = en loads `sqlite/basmaster-en.sqlite3` instead of `sqlite/basmaster.sqlite3`), and through it every reader of `master_text` (`StringDB::GetNativeString`, `StringDB::GetList`); the data check (`CVerifyTask`), which fetches every new member.
- **Guest behaviour:** the 3.7.0 client never sets `CLanguage::Current` (0x100: no postfix), so it never asks for a `-en` file; a client with it set (the port's and soa-emu's `--lang en`, a client change logged under its own entry) tries `<name>-en.<ext>` first and falls back to `<name>.<ext>`.
- **Change:** with `--english` the server's CDN serves new members beside the Japanese files (docs/server-rules.md#english): `sqlite/basmaster-en.sqlite3`, the served master (after every override in this section) with English in the `text_value` of the `ja_` rows the English text table (`data/english/master-en.tsv`) translates, and new `ja_` rows for the client strings' new ids (`port_en_*`). Also `Scenario/TS_xxxx-en.msgp`, a story file with English in the `text_value` of its rows, for each story file whose every Japanese line has English (docs/server-rules.md#english-story). Ids, other columns and the other tables are the served master's. Every client fetches the new members at its data check, a Japanese one too (it doesn't read them).
- **Why not in a response:** the text is the client's own master copy, which the server already serves edited; a file per language is what the client's loader already looks for (docs/english.md 6.3, 6.6).
- **Switch:** `--english` (soa-server; soa's in-process server: `--english`, and `--lang en` once that option sets it). Off: the CDN is unchanged.

### Sphere 211 season dates moved in the client's master copy (agent `sphere211`)
- **Symbols affected:** the readers of `master_sphere211.opened_at` / `closed_at` / `ranking_opened_at` / `ranking_closed_at`: `MissionUtility::GetExtraDungeonList` (the home's スフィア211 button and the extra-dungeon menu lead in only when a season's window covers the client's clock), `MissionUtility::Sphere211ClosedTime` ("シーズン終了まで あと N日"), the ranking screens.

The other rows and all client code are unchanged.
- **Why not in a response:** the master DB is the client's own copy, not a response; serving it with the season's dates moved is what the online server's data would have been on that day.
- **Also (agent a5-sphere):** before the first season (days the replayed calendar maps to 2019, e.g. Oct 1 - 2 and Oct 7) the season of the same date a year later is served, so every day has a season; and the last season's empty `master_sphere211_ranking_reward_id` is filled with the group of the latest season before it that has one (`client_ranking_groups`), so the season-end dialog (`CSphereRankingResult`, which reads the reward from `Sphere211EndResult.previous_season_id`'s row) shows what the server grants when the repeated last season ends. ## Code changes
The server core made none: in-process every other behaviour is the local server answering on the port's `FakeApiCaller` route (`--server inproc`).

### Local-server refusals reach the client's error handling (agent `server-missions`)
This is port plumbing on the port's own `FakeApiCaller` route, not a change to game logic. It's listed because it changes what the player sees with the in-process server: an error dialog instead of a silent success.
- **Symbols:**
  - `FakeApiCaller::IsSuccess`, `IsFailure` and `ErrorCode` (the port's native hooks, `port/src/native/api/fakeapi.cpp`);
  - the port's `ServeProgress`, which calls the guest's `ErrorHandler::Handle(fid, Status)`.
- **Guest behaviour:** `FakeApiCaller`'s queries return the constants 1 / 0 / 0, so a request on that route always succeeds. The network path (`NetworkApiCaller`) reports the server's error code, and `CApiNotify::OnProtocolError` passes it to `ErrorHandler::Handle`.
- **Change:** when the local server refuses a request (`server::error_code(fid)` ≠ 0):
  - `ServeProgress` calls `ErrorHandler::Handle(fid, Status = code)` while the request is still in flight, as `OnProtocolError` does, and sets `CApiNotify+0x514` = code;
  - it doesn't call the `On*Res` handler, as on the network path;
  - `IsSuccess` / `IsFailure` / `ErrorCode` report the failure.

  The client's unchanged `CErrorHandlerWrap` then shows `master_text` `error_message_text_<code>` and does what its own tables say. After a refused `MissionStart` (e.g. 10004 スタミナが不足しています), OK goes back to the title (the guest's `HndlType` table). A gacha screen's dialog just closes.
- **Why not server-side only:** the route has no error channel. The canned `FakeApiCaller` answers every request as a success, whatever the body says (`status` in the body goes to `CParameterManager+0xb728`, which the callers don't check).
- **Switch:** the in-process server (`--server inproc`, the default). Without it, `server::error_code` is always 0 and the queries return 1 / 0 / 0 as before.
- **Evidence:** `work/decomp/server-missions-err-{ehw,b,cb,g}.resolved.c`; docs/server-rules.md#server-missions, docs/server-rules.md#refusals.

### `IApiCaller::UpdatePartySet`, `SetAssist` and `UpdateView` on the FakeApiCaller route
- **Symbols:** `IApiCaller::UpdatePartySet(PartySetInfo const&)`, `IApiCaller::SetAssist(unsigned long, unsigned long)` and `IApiCaller::UpdateView(Common::ViewFlagType, unsigned long)`: base-class stubs that `FakeApiCaller` inherits (it has no such methods).

- **Why not server-side:** this *is* the route to the server. `FakeApiCaller` never implemented these requests, so without the change the client never sends them.
- **Switch:** the in-process server (`--server inproc`, the default; it turns on the FakeApiCaller route).

### Word wrap at spaces (E10 b)
- **Symbol:** `Framework::Cocos::CCocosLabel::DrawSelf()` (ELF 0x1eaca74), hooked (`platform370/src/text_370.cpp`).
- **Guest behaviour:** the client breaks lines only at `\n` (`TTextCompositor<Utf8>::ComposeString_`); `DrawSelf` measures the text (`CDirectAofTextRenderer::CalcStringRect`) and either shrinks it into a fixed box (`IsCustomSize` +0x280 with +0x282) or lets the label grow with its text, so a long English line runs off its box or the screen (english.md 2, experiment 2; 3.2).
- **Change:** with `--lang en`, before the original lays a label out, each line of its text that is wider than the label's room is broken at spaces (greedily, by the shared breaker `soa::text::break_lines` of `common/include/soa/line_break.h` with the existing breaks kept; the text is set again with `\n` in it). Widths are the client's own: `CalcStringRect` on the label's renderer with its font size, in the label's units. The room: a fixed-size label's box width (and for a label that shrinks its text, the wrap is kept only when the text then shrinks less: one-line buttons stay shrunk); any other label's room on the screen, from its world position, scale and anchor to the edges of the 720-wide design area (12 units of margin). Lines with Japanese (kana, kanji, full-width forms), texts without a space, a word wider than the room, and tag-mode labels (+0x281, `<font>` markup) are left as the original lays them out. Wrapped texts are cached by text and room; a label that moves after its first draw (a header line placed after its title, a panel sliding in) is wrapped again from its original text at each new room.
- **Rules added after the screen sweep (english.md 7.12):** a screen label is wrapped only once it is drawn twice at the same world x (labels that slide in were wrapped at their first frame's room; until it settles the label is laid out again each frame). Wrapped lines are balanced: the narrowest width that keeps the greedy line count. A menu's header description (`Node_1` / `Node_maintitle` `/Text_2` of the `*_common.csf` menus, `gacha_main.csf` `subtitle/text2`) and a short label (up to three words) wider than its room stay on one line and are shrunk into it (at least 50% / 60%; else wrapped): the label is made a fixed box of the room's width (IsCustomSize, +0x282) and gets its own fields back when its text changes. A fixed box that shrinks its text and has no line break is re-broken for the largest scale (`fit_box`, E12's rule). A dialog's message (`pop1/window/Text`, anchored at its centre) taller than the room between the window's top rule (`line_1`) and its buttons (`Button_*`, else `line_2`) keeps its lines and is made a fixed box of that room that shrinks its text, centred where it was (the user: shrink the font, don't shorten; e.g. `uimsg_mastary_dialog0` at 73%).
- **The room from the layout (english.md 7.15):** a label whose size follows its text also gets the room its layout leaves it (`text::layout_room`, `platform370/src/text_370.cpp`): its siblings on its row (shown: own visibility +0xd8 bit 0, opacity +0xbc) end it where they begin (a label sibling grows from its anchor too, so two labels that face each other share the gap at one scale; a sibling that spans the label's anchor, such as a plate behind it, or that would need less than 40% is not in the way), and so does its parent's box when the parent has a size and holds the label's anchor (a button, a list row, an icon), 6 units in. A label so bounded is shrunk into that room (made a fixed box of the room's width, IsCustomSize +0x280 with +0x282; its own fields back when its text changes): against a sibling always (the header title before its description, a button's text beside its icon, a caption before its value, the birth-date table's cells); against its parent when one line shrinks to at least 75% (60% for up to three words), or to at least 50% when its lines broken at the frame would leave its free band (the frame's height, below the sibling above it: a list row's description). Texts of any length are considered ("S Stamina", "Awakenings"), with two ASCII letters in a row and no Japanese. A tag-mode label (`<font>` markup, DrawSelf measures it without the tags) is shrunk into its room the same way, never broken (the character guide's line). A dialog's message (`pop1/window/Text`) with the data's own line breaks keeps them and is shrunk into the room (to at least 60%) instead of being broken into more lines; its room above the buttons also counts the `menu_pop_line` rules (`gacha_result.csf`). The room is scanned while the label settles (the label at the same x with the same room twice) and every 32nd frame after. With `--lang ja` none of this is installed.
- **Story window:** its labels (the window's message label and `Append`'s clones, named `AppendMessage`) are left alone: the data breaks story lines and E13 below scales them. A text revealed a character at a time is never re-broken at run time, so words don't jump between lines while it appears.
- **Per-label state:** what the hook remembers about a label (the text it set and the original; E12's kept box) is keyed by the label's address and forgotten when the label is destroyed (`CCocosLabel` D1 @ ELF 0x1eac5b8 and D0 @ 0x1eac5ec, hooked: the state is dropped, then the original runs), so a new label at a freed label's address never inherits it. The result caches are bounded (least recently used out). The label fields are the recovered layout `platform370/include/platform370/cocos_layout.h` (shared with the port's `ui/cocos_node.h`).
- **Not for the home's speech box:** its two `talk_text` labels are fitted instead (E12 below).
- **Why not server-side:** pre-breaking every text would need each label's box per screen (english.md 4.3); the client knows it at draw time. The data side still pre-breaks story lines (E7).
- **Switch:** `--lang en`.

### The home's speech box: English lines fitted to it (E12)
- **Symbol:** `Framework::Cocos::CCocosLabel::DrawSelf()` (ELF 0x1eaca74), the E10 b hook (`platform370/src/text_370.cpp`, `fit_talk` / `text::fit_box`), for two labels only: `talk_menu_gp/talk_frame/talk_text` (the home) and `talk_menu_talkmode/talk_frame/talk_text` (Talk Mode) of `UI/etc2/home.csf`, told by their node names (the `std::string` at +0x28 of the label, its parent and grandparent; parent at +0x08). `CHome::PlayTalk` (@01aef4e8) is the only code that names them.

- **Proof:** `soa_text_tests` (T0 `line-break`: `fit_box` with a fixed-advance measure, and the shared breaker's vectors); selftests `platform370/lang-label-state`, `lang-cache`; shots `work/english/homefit/` (local), with `SOA_TEST_TALK_IDS` (a test switch: the box shows the master text of the given ids in turn).
- **Switch:** `--lang en`.

- JNI references with a zero low byte: the client reads a returned `Boolean`'s reference as a boolean.
- The missing ARM64 Top Byte Ignore in the JIT's memory callbacks.

Both have since been fixed in the runtime (agent `r2-runtime-fixes`, 2026-10-01; `runtime/README.md` "Platform fidelity"). Every JNI handle now has a non-zero low byte, as on ART, and data addresses ignore their top byte, as on ARM64 Linux. **These are platform-fidelity fixes, not client changes:** the game code runs unmodified and now sees what a phone gives it. soa-server still closes the connection after a ProtocolError; that is a server choice, and soa-emu no longer needs it.

## Emulator viewer (3.8.0) (`soa-viewer`, `emulator-viewer/`)
The viewer runs the offline 3.8.0 `libSOA.so` (from the XAPK's `config.arm64_v8a.apk`) **fully unmodified**: no guest-code patch, no native replacement, no restore image, no server. Only the platform layer under the game is emulated, and the runtime (`runtime/`, built for this library's imports and Java methods, Play Core included) already provides it. The viewer adds one platform answer of its own (`emulator-viewer/src/net_offline.cpp`, registered through `hle_add_registrar`, active only in `soa-viewer`). Details are in `emulator-viewer/README.md` "What is viewer-specific".
