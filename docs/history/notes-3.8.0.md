# Notes: 3.7.0 vs 3.8.0 (moved from docs/notes.md)

> History: these sections of `docs/notes.md` compared the offline 3.8.0 build with 3.7.0 and planned the restore of the 3.7.0 campaign onto 3.8.0; the port no longer uses 3.8.0 (it runs the 3.7.0 client). Current docs: [docs/notes.md](../notes.md), [port/README.md](../../port/README.md); the full comparison: [libsoa-3.7.0-vs-3.8.0.md](libsoa-3.7.0-vs-3.8.0.md).

## 3.7.0 vs 3.8.0: what the offline build changed

The full write-up, grouped by subsystem with the port's response to each change, the added / removed code, the master-DB and asset differences and an index of all 419 changed functions, is [`docs/history/libsoa-3.7.0-vs-3.8.0.md`](libsoa-3.7.0-vs-3.8.0.md). This section is the short version.

Measured with `tools/verdiff.py` (2026-09-29); the full, regenerable output is `work/verdiff/report.md` (per class), `changed.tsv` (machine-readable), `layout.tsv`, `strings.tsv`, `vtables.tsv`, `only.tsv`, and one normalised diff per function in `work/verdiff/fn/`. Side-by-side Ghidra output of 32 key functions: `work/decomp/v370-<Class>__<Method>.c` / `v380-...`; more with `tools/verdiff_decomp.sh <mangled>...`, or one build at a time with `tools/decomp.sh --v370 ...`.

**Method.** Every function present in both builds is disassembled and normalised: PC-relative addresses, GOT loads and branch targets become the symbol, string, GOT symbol or constant bytes they reach; branches inside a function are aligned across the two builds; `__LINE__` arguments of `gDoAssert` and the debug allocators are masked; lld's Cortex-A53 erratum veneers are folded back. Unnamed functions are found from BL targets, code pointers and `.eh_frame`; `std::function` lambdas are named from their `__func` typeinfo (`Class::Method::[lambda #k]`). What's left is behaviour. 102k function bodies were compared: **419 differ**, 118 of them with the same size (the size diff missed those). Of the 419, 169 are lambda slots in about 40 enclosing methods, 56 are runtime or toolchain noise (libgcc unwinder, libc++ locale tables, a few mispaired static functions), and the rest are named game functions in 57 classes.

**Version stamp.** `CBuildInfo`: 3.7.0 is build 3152, SCM revision 90144, "3.7.0-review", 2021-04-05; 3.8.0 is build 67, revision "3.8.0", 2021-06-07.

### What was cut or altered, by feature
- **Clock frozen at the end of service.** 3.8.0's `BAS::LocalTime(bool)` (3.7.0: `LocalTime()`) and `CTimeUtility::NowTime` return `master_global.service_stop_day` (2021/06/24 14:30:00, also present in the 3.7.0 DB, where the code ignores it) instead of `time()` + the server offset (`CServerTime::FixTime`). 30 time helpers in `CTimeUtility` / `CUIUtility` (AP regeneration, "remaining time" texts, campaign windows, coin sales, footer badges, `IsWithinDay`) now call `NowTime` instead of `LocalTime` + `FixTime`. Server-side route for a live clock: drop or move the `service_stop_day` row (master data), no code change.
- **Missions.** `CMissionMenu::NextPhase`: 3.7.0 copies the selection into `CParameterUI` before leaving the menu (the selected mission's id → `+0x1a0` and name string → `+0x158`, two ids from the menu's selection lists → `+0x150` / `+0x154`, the selected helper index + 1 → `+0x1b0`, the helper's `NpcOrRentalId` → `+0x1b8`, its kind (2 = self, else `IsNPC`) → `+0x1c0`), skipped for next-phase values 4, 11 and 16; 3.8.0 drops the whole copy, so no mission start is prepared. `CMissionSelectPart::CreateList` / `Initialize` and `CScenarioLibrary` lost the downloaded-episode and maintenance checks (`IsDownloadedEpisodeState`, `IsPartialMaintenance`, `IsEpisodeMaintenance`) and the tutorial hook; `CScenarioLibrary::Progress` calls the new `RequestListLocal` / `CreateStoryListFromSqlite` instead of `RequestListReceiveApi`. `CUIUtility::CommonResourceButtonMissionData::Initialize` grew local `…MissionLocal` variants, and `SetupCommonResource_ButtonMission` gained a `bool` parameter.
- **Party building.** `CPartyComposition` was cut to a character list: `Progress` 7,156 → 1,044 bytes, `Setup` 4,416 → 608. Gone: the party-select top scene (`InitializeUI_PartySelectTop`, `PartySelectStart`), the scene replacement and detail dialog, stamp selection, the sort buffer from the parameter list, the mission-detail dialog, and the edit / custom / evolution / mastery / awakening / stamp-edit / battle-simulator / dictionary / clan buttons (their `uimsg_*` strings). 25 lambdas are gone with them (16 in `Setup`, 9 in `Progress`). `Initialize` now builds a `CCharacterPictureBook` instead. The object layout is unchanged (0x610 bytes), so 3.7.0 bodies can run on 3.8.0 objects.
- **Adjutant (home assistant) select.** `CAdjutantSelect::UpdateList` 1,596 → 596 bytes (it no longer builds `tCharaData` from the roster; the new `CreateCharaList` builds it from master roles). **The layout changed**: the object is 0x410 → 0x420 bytes, and the fields move (`0x128/0x130/0x138/0x140` → `0x140/0x148/0x150/0x158`, then +0x10 for everything from 0x150 on); a new zeroed pointer sits at `0x158` in 3.8.0. 11 of 12 methods differ only by these offsets. `CHome` itself keeps 0x530 bytes.
- **Title, login and new player.** `CTitle::Setup` 3,068 → 1,584: the player-id display (`IsLocalKVSPlayerID`), the resource-cache check, the update panel, the service-end dialog, the title movie and the refund (`Button_refund`) path are gone; 4 lambdas removed. `CPhase_Login::Progress` dropped the online steps (the crypted player/session properties, `SetLocalKVSPlayerID`, `SetMissionRestart`, `CPaymentManager::Initialize`, the select-all-download query, 6 lambdas) and added the stand-alone new-player flow: `IsLocalKVS_StandAloneNewPlayer` / terms-of-use keys, `CPlayerInitializeMenu` created with a dialog type, and the three starter roles `offline_Character_1..3` from `master_global` (only in the 3.8.0 DB). `CPhase_Login` grew 0x28 → 0x30 bytes (one new byte flag at +0x28). `CPlayerInitializeMenu::Initialize` 3,608 → 2,180.
- **Phase flow.** `CPhase::Switch` lost the Relogin, SyncServerTime (`CheckSynkServerTime`, DNS cache clear) and TutorialNext phases. `CPhase_TutorialNext::Progress` no longer calls `Net_Tutoflag`. `NetworkApiCaller::BeginBridge` lost its "already bridged" shortcut (3.7.0 copied the player id from `CParameterPlayer` into the caller and completed at once).
- **Tutorials.** `CTutorialManager::IsStartTutorial`, `IsStartTutorialNext` and `IsExistMenuVoiceMask` return 0; `SetBattleTutorial_UI` is a bare `ret`; `ProgressUI`, `IsFinishUI` and `IsBusy` were simplified. `CHome`, `CPartyComposition` and `CMissionSelectPart` no longer set up tutorial UI.
- **Home.** `CHome::Setup` changed its button layout (`main_button%d` loop → `main_button2`; the event-mission and extra-dungeon openers and `UpdateCampaignBadge` are gone), and 18 of its lambdas differ. `UpdateBadge` lost the new-story-part animation (`story_2nd_newpart_*`), `Progress` / `Initialize` / `PopupProgress` lost the tutorial and network-error handling and now save to the local KVS, `GetAdjutant` consults a `master_global` date, and `SetTalkMode` / `SetVisibleTalkMode` now hide the `Node_5_studiomode` node (`CUIUtility::Show(..., false)`) where 3.7.0 showed it. `CCommon::UpdateMyStatus` lost the player title, galaxy pass and subscription items. `CCommon::Initialize` loads the offline footer layout `common_sa` (home / character / other) instead of `common` (home, character, item, gacha, shop, other). Under `--restore` all three classes (`CHome`, `CCommon`, `COtherMenu`) run their 3.7.0 code (restore370 groups `home`, `common`, `othermenu`; `docs/client-changes.md`).
- **Favorability.** `CParameterUtility::GetFavorabilityLevel` / `GetFavorabilityParam` / `GetFavorApBonusBySameRoleID` / `GetFavorDropIconImageName` and `tCharaData::GetFavorabilityLevel` / `GetAssistesFavorabilityLevel` / `InitializeFromMaster` replaced `IsOpenFavorability` + the stored per-role favorability data with `GetEnableFavorability` and much shorter bodies. The sort dialog lost the favor-level filters.
- **Character book and details.** `CCharacterPictureBook::OpenNotHaveDialog` 1,744 → 464 and `CreateCollectList` changed (`PersonModel::FindPersonInfoFromID`, which only 3.7.0 has, is no longer used); `CollectData` grew 4 bytes (0x54 → 0x58 copied). New in 3.8.0: `OpenCharaDialogForSA`, `GetCharacterListForSA_FromMasterIdList`, `CreateBufferFromParameterListForSA`. `CDetailDialog_Character::Start` lost the rarity-over checks; `CUISort::CreateCharaParameter` sorts by `MasterRollId` instead of `CharaId`.
- **Settings.** `CSystemSettingMenu::ProgressResetApi` 312 → 48: it resets locally (`CUIUtility::ResetSettingMenuParameter`) instead of calling the reset API. The menu-voice KVS keys were renamed to `BAS:IsMenuVoice{Coro,Eveleash}Enable_Ver2`. The sound and graphics pages grew (rows re-laid out), and the other / event / battle-settings lambdas changed. `CUIVoiceManager::MenuID` gained one value (the bound checks go from 0x11 to 0x12, and the title voice id from 0xd to 0x13), so **menu-voice ids differ between the builds**.
- **Platform services, stubbed.** Google Play achievements (`BAS::*Achievement*`, `ReportAchievement`), game-services sign-in, local notifications (`Schedule/UnScheduleLocalNotification`), and location / GPS (`BAS::Location::*`, `BAS::LocationUtil`, `CTest_Location`) return constants or nothing. The 47 functions that exist only in 3.7.0 are mostly their `Platform::Android` JNI wrappers.
- **Web views.** `WebViewUtility::GetWebInfo` / `OpenBrowser` and `CWebView` show local HTML (`local_html_{copyright,credit,kiyaku}_by_android`) instead of the online pages; `BAS::WebView` and `tWebInfo` gained a parameter.
- **Resources.** 3.8.0 adds Play Asset Delivery (`CGameAssetPackManager`, the `playcore` library: the 201 functions that exist only in 3.8.0, 3 more static initialisers). `CGameResourceManager` grew 0x70 → 0x78 bytes (an `m_pAssetPack` pointer). `Initialize` / `Release` / `CheckResourceStatusByFileName` / `AddDirectFile`, `CSoundManager::PlayBgm`, `CMovieManager::PlayMovie` and `CAnimationModelObject::Progress_Load` consult the asset packs. `CPhase_DataDownload::Progress` dropped the old-version-file migration. `CGame::OnPause` / `OnResume` forward to the asset-pack manager.
- **Unchanged.** All vtables of classes present in both builds (slot for slot, by target), `JNI_OnLoad` and its two natives (`BluetoothA2dp{Playing,NotPlaying}`), the battle code (`CBattle*`), the API response handlers (`CApiNotify`), `NetworkApiCaller` apart from `BeginBridge`, and the master-parameter loaders (3.8.0 only adds three offline queries, `ParameterFormMasterScenarioLibraryIDList` and friends).

### Layout check (can 3.7.0 code run on 3.8.0 objects?)
The `operator new` sizes before each constructor call, and the field offsets in same-named methods, are compared for all 57 classes with changed functions (`work/verdiff/layout.tsv`). Every class keeps its size and field offsets **except**:

| Class | 3.7.0 → 3.8.0 | Consequence |
|---|---|---|
| `CAdjutantSelect` | 0x410 → 0x420; fields from 0x128 remapped (see above) | 3.7.0 bodies need their offsets remapped, or the whole class restored together (including the constructor and `CHome`'s `new`) |
| `CGameResourceManager` | 0x70 → 0x78 (asset-pack pointer at the end) | Harmless for 3.7.0 code, which doesn't touch the tail |
| `CPhase_Login` | 0x28 → 0x30 (one flag at +0x28) | Harmless for 3.7.0 code |
| `CCharacterPictureBook::CollectData` | 4 more bytes at the end (0x54 → 0x58) | Copies differ; the element size of the collect list changes |
| `CUIVoiceManager::MenuID` (an enum, not a layout) | one value inserted before the title voice | 3.7.0 menu-voice ids must be translated |

`CPartyComposition` (0x610), `CHome` (0x530), `CMissionMenu` (0x1720), `CMissionSelectPart`, `CTitle` (0x940), `CPlayerInitializeMenu` (0x520), `CScenarioLibrary`, `CTutorialManager` (0x160), `CSystemSettingMenu`, `NetworkApiCaller` (0xde0) and `CParameterUtility::tCharaData` are the same in both builds, so their 3.7.0 bodies can be installed directly on the 3.8.0 symbols. The other offset differences the tool lists (`Aska::ShadowManager`, `Aska::SoundUtility`, the Cocos easing templates, `CPlayerInitializeMenu`, `CScenarioLibrary`, `CSortDialogWrapper`, one or two accesses each) aren't fields: they are low-12-bit page offsets whose `adrp` is in another block, or short-string terminators of different lengths (checked by hand for `ShadowManager` and `CScenarioLibrary`).

## The original campaign (3.7.0)

Investigated 2026-09-29 for the restore run (`--restore`). The 3.7.0 story campaign's screens are all still in the 3.8.0 client, unchanged; the offline build only cut the way in (the episode list) and the hand-over into a battle, and the server data that fills them never arrives offline.

### Flow and classes
- **Home → Mission** (`tap:90:1080`) → phase 8 `CPhase_SelectPart` → `CMissionSelectPart`: the episode list, one banner per `master_selectpart` row (`chapter_0` = Episode 1, `menu_type` 0; `chapter_1` = Episode 2, 1; `Episode03`, 2). `CreateList` maps `menu_type` to a mission type through a 3-entry table (0 → 0 planet missions, 1 and 2 → 3 world map; identical in both builds).
- **Tapping an episode** (a lambda in `CMissionSelectPart::CreateList`) stores the part's mission type in `CParameterUI+0x140`, its id in `+0x14c` and the next phase in `CMissionSelectPart+0x188`, which `CMissionSelectPart::Progress` state 4 switches to (`CHaveCommon::SetToNextPhaseAndStopBGM`).
  - **3.7.0: phase 5, `CPhase_Mission`** (instruction `mov w9, #5` at 3.7.0 0x1ab49b8). **3.8.0: phase 7, `CPhase_ScenarioLibrary`** (`mov w9, #7` at 0x1abc36c), the offline "scenario library" that only replays scenes. This one instruction is the whole difference in the lambda; the verdiff size list doesn't show it (the lambda has no symbol and kept its size).
  - The back button's lambda: 3.7.0 returns to `CParameterUI+0x1d4` (the phase the menu came from), 3.8.0 always to 4 (home).
- **`CPhase_Mission` → `CMissionMenu`** (0x1720 bytes, same layout in both builds; the "planet select" bridge view with 出撃 / シナリオライブラリ / 実績 / Ep選択): planets (`CreatePlanetList`, from `CParameterUtility::CollectEffectivePlanet` = `master_planet` × `master_area` by date, filtered by the server's `ActiveMissionList.Planet`), 出撃 → the planet's mission map (areas and mission nodes with CLEAR / New marks, story nodes with a book icon, the clear rate), a node → `StateDetailMission` (first-clear rewards, drops, "シングルプレイ開始"), then the rental list (`レンタルキャラクター`, filled by the server's follow / rental data; "選択しない" skips), then the party select (`パーティ選択`: `CParameterUtility::CreatePartyData` over the server's `PartySet`), ミッション開始 → 決定.
- **Episodes 2 and 3** (mission type 3) use `CWorldMapMenu` (60 functions, unchanged): world maps (`master_world_map`, `_base`, `_cell`), group missions (`master_world_map_group_mission` / `_mission`), a single progress counter per episode (`CPlayerInfo.world_map_progress` / `world_map_progress_ep3`, compared with `master_world_map_progress.progress`) and sub-stories (`BAS:LastViewWorldMapPopSubStory`). It asks the server first: `CWorldMapMenu::CallReceiveApi` → `CErrorHandlerWrap::Auto(FunctionID 0x15a9bdbd = GetWorldMapInfoList, ...)`. `FakeApiCaller::GetWorldMapInfoList` only returns a Status, so the port's fake server doesn't answer it yet.
- **Leaving the menu: `CMissionMenu::NextPhase(int)`.** 3.7.0 (1464 bytes) copies the choice into `CParameterUI` unless the next phase is 4, 11 or 16 (mask 0x10810): mission id `+0x1a0` (from the mission list `+0x4c8`, 0xb8-byte `tMissionParam`, id at +0x98, selection `+0x770`), its label string `+0x158` (unless `CParameterUI+0x1d4` is 7), area `+0x154` (list `+0x4b0`, 0x58 bytes, id at +0x44, selection `+0x76c`), planet `+0x150` (list `+0x498`, 0x40 bytes, selection `+0x768`), party number `+0x1b0` (selection `+0x77c` + 1), and the party's helper (`tPartyData` list `+0x4f8`, 0xb4d0 bytes, helper `tCharaData` at +0x8798): `NpcOrRentalId` → `+0x1b8`, kind (2 self, else `IsNPC`) → `+0x1c0`. 3.8.0 (640 bytes) keeps only the remainder (input lock, the multiplayer-host flag, the fade / `sbtitle_in` animation, `+0x2ec` state). Without the copy, `CPhase_Battle` starts mission 0 ("invalid mission stage").
- **Battle → result → back.** `CPhase_Battle` → `CStageManager` → `MissionStart(type, mission id, party number, helper, …, select part id)` → battle → `MissionEnd(mission id, select part id)` → the result pages → phase 5 again: the mission map shows the new clear and the next unlocked node.
- **Story missions** (`master_mission` rows with a `talk_event_id`, labels `mcNN_NNN`; world map groups `…_msNNN` of mission type 1): the detail has 閉じる / ストーリー開始; `NextPhase(3)` → phase 3 `CPhase_Event` plays the scene (script `Script/<talk_event_id>.msgp`, talk file `Scenario/TS_NNNN.msgp`). **3.7.0's `EventScenario::CEventScenario::Exit`** (984 bytes) ends with `CErrorHandlerWrap::Auto(0x1d00a78c = EndMissionTalk, …)` when `CParameterUI+0x1a0` holds a mission: that is how the server learned the story was seen. 3.8.0 (648 bytes) dropped it; nothing in 3.8.0 sends `MissionTalk` or `EndMissionTalk`.
- **The chain** is data: `master_mission.unlock_mission_id` names the mission whose clear unlocks each one (`visible_mission_id` likewise for visibility). Episode 1: `mc00_010` (story) → `mc00_015` → `ms00_001` / `mc00_025` → `mc01_010` → `mc01_020` → `ms01_001` → `mc01_025` → **`mf01_001` (1-05, the first field battle)** → `mc01_030` (story) → `ms01_002` → … 11 planets (`planet00` prologue … `planet10`), 613 missions.

### Feasibility and what the restore does (`--restore`)
- **Server side (no client change):** `ActiveMissionList`, `PartySet`, `Player.view_status*`, `MissionParameter` and the progress on `MissionEnd` / `MissionTalk` are all plain response data; `server/src/api_campaign.cpp` builds them from master data plus a persisted clear set, and the fake server route delivers them (a `GetPlayer` request queued after the save's roster loads stands in for the 3.7.0 login responses).
- **Client side (unavoidable, logged in `docs/client-changes.md`):** the episode tap's next phase (5 instead of 7: one instruction) and the `CMissionMenu::NextPhase` hand-over. No server data can reach either: the phase is a constant in the lambda, and the hand-over copies client-side menu state.
- **Also client-side:** the end of a story scene (`CEventScenario::Exit` lost its `EndMissionTalk`); restored by passing the mission to the local server after `Exit`.
- **Episodes 2 and 3:** with `GetWorldMapInfoList` answered (`ActiveWorldMapMissionList` + `Player.world_map_progress*`, only the requested episode's maps: the argument is the `master_selectpart` id), the world map opens. Episode 2 shows ダフティーネ宙域 (`map_planet_00`) with one STORY point and 惑星遷移 locked; its first story (m02_01_ms010) plays the opening movie `m2011_010.mp4`. Episode 3 shows the アズライト星系宙域 map with a STORY point, the mission list (メイン / サブ / フリー / すべて), `1-01 離別` (m06_01_ms020) and its story (リーシュ's scene, then the movie `m6011_010.mp4` from the download set). The scenes used to stop at the movie. Two port bugs in the movie player (`frontend/movie.cpp`, `main.cpp`) caused it, both fixed by agent gaps-core:
  - **Audio stall.** Movie audio was paced only by the SDL audio callback. The decoder stops reading at 1 s buffered, and the movie counted as done only when video, audio and the buffer were all finished. When the callback didn't drain the buffer (no device, a failed `SDL_OpenAudioDevice`, a stalled WSLg sink; the `audio peak 0.00` perf lines during a movie), the movie never ended, and the ffmpeg process was still writing audio minutes later. Now audio is paced by the wall clock too: samples the device hasn't taken 0.5 s after they are due are dropped. The selftest `frontend/movie-ends-without-audio-device` plays a 2 s clip with the mixer stalled and fails without the fix.
  - **Start race.** `PlayMovie` (game thread) set `movie_playing` before `movie_start` ran (ffprobe takes a while), and the main loop's end check (`movie_playing && !movie_active()`) could fire in between. It "ended" the movie at once, and `MovieFinished` returned true while the movie kept playing, unwatched. `movie_playing` is now set only once the movie runs.
  - `port/scripts/episode_movie_session.sh <soa> <out> <scratch> 2|3` plays each opening story in auto mode through its movie to `EndMissionTalk`. Movie assets named `builtin_data/...` are also looked up in `--download-dir`.
- **Result (2026-09-29):** from the title, Mission → Episode 1 → planet select → planet Mere → the mission map → 1-05 → single play → party 1 → the battle (MissionStart for the chosen mission) → win → MissionEnd → back on the map with 1-05 CLEAR and the next story mission New; `port/scripts/campaign_session.sh`.
- **Not yet:** Episode 2 and 3 play-through beyond the first story (free-battle cells and group progress aren't verified on screen), rewards (`MissionEnd` is still the canned response: FOL, one item), stamina, real party stats (the battle party is still the canned `BattleParameter.PlayerCharacter`).

## From port/README.md: the offline build in the pre-rebase port

How far each gets (2026-09-28):
- **Battle:** without a server, `MissionStart` fails and the game shows "communication error 1002". With `SOA_FAKE_SERVER` + `SOA_DOWNLOAD_DIR` and `mission:mf01_001`, the whole mission plays: `MissionStart` brings the party (the save's roster as `BattleParameter.PlayerCharacter`), both stages load and are fought (the party acts on its own), then `MissionEnd` and the Mission Result screens.
- **Gacha:** without a server: error 1002. The offline APKs lack the gacha screen's layouts (`UI/etc2/gacha_*.csf`, `summon_start.csf`, ...), so the gacha needs `SOA_DOWNLOAD_DIR` in any case (`gacha_session.sh` defaults it to `work/download-3.7.0`): without them entering the gacha crashes (SIGSEGV at 0x8 in `CResourceManager::crResourceElementDirectFile`, which, like the guest, doesn't check for a missing file). With `SOA_FAKE_SERVER` (+ `SOA_DOWNLOAD_DIR` for banners and the summon), the port serves `GetGachaInData` (`gacha_in_data.msgp`: the open-gacha hash list and a wallet of 100000 紋章石), the tabs list the gachas, and a 10-draw runs through the summon presentation to the result list.
- **Debug windows:** open, draw (frames only, no title text), and close with `PostQuitMessageToAllWindows`.

Known limitation of that port:
- **Missing sound data.** The APKPure XAPK contains only the install-time asset pack. The *fast-follow* pack (`Sound/*.aac`: most BGM, including the home screen's) and the *on-demand* pack (`Sound/TS_*.spk`: talk-scene sound) were delivered separately by Google Play, so those sounds are silent. The title-screen BGM and system sounds are in the base APK and play.
  - If you have the pack APKs (on a device where Play installed them: `/data/app/<pkg>/split_assetfastfollow.apk` and `split_assetondemand1.apk`), put them in `--apk-dir`. Either `assetfastfollow.apk` or `split_assetfastfollow.apk` works. They're extracted once into the data directory and reported to the game as installed.
