# Plan: rationalize the local server's state schema

**Multiplayer comes after this plan (the user, 2026-10-03):** the schema changes multiplayer needs are planned separately in [`PLAN-multiplayer-schema.md`](PLAN-multiplayer-schema.md) (steps M1…) and run **strictly after S12** (and R12, R17, S11+R19) have landed, starting from this plan's final schema. Nothing here is changed for them: S3–S12 proceed as written; where one makes an M step costlier, the M step says so.

Status: plan only (2026-10-02, agent `schema-plan`, branch `port/schema-plan` off `linux-port` ec4354c). No server code is changed by this plan; the first commit that implements it is step S1 below.

**Scope.** The local server's persistent state, `DATA/server.sqlite3` (soa's in-process route; `soa-server --db`), created and used by the server library in `server/` (and `server/net/game.cpp` for soa-server's `wire_device`). The master DB (`data/basmaster-3.7.0.sqlite3`) and the gacha pools DB (`data/gacha_pools.sqlite3`) are read-only inputs and out of scope, except as the targets of references.

**Trigger.** Favor is stored in two places: `roster.favor` (server/src/server.cpp:415, in the first server commit 0802915, never read or written by the server) and the real `favor` table (server/src/favor.cpp:193, keyed by `same_role_id`). The inventory below shows this is one of several dead or duplicated facts, and that the schema has no versioning, no foreign keys, and module tables created lazily from 10 call sites.

**Summary of the findings** (section 2):

- 1 dead column and 4 dead tables: `roster.favor`, `gear`, `box_gacha` and `planets` (seeded, never read) from the first commit 0802915, and `view_flags` from 0add5c3. `mission.best_rank` and `sphere.revive_count` are written only by tests (the latter was a rules gap, R18a: F1; Sphere211MissionStart / ReturnSphere211 write it since 2026-10-03, agent srv-bugfix-1).
- Facts kept in two places: favor (`roster.favor` / `favor`), the UI-tutorial words (`meta` / `view_flags`), a character's assist (`assist` beside the roster), and the party members (`party` + `party_member` + `party_set`).
- 7 `Player` fields live in `meta` text keys. One of them, `view_status`, is a u64 stored as decimal text because it doesn't fit SQLite's integer type.
- Two tables are split off their core table only because modules can't alter it: `roster_ext` and `play_ext`. `present_texts` is split off `presents` for the same kind of reason.
- No foreign keys at all, and 0 used as the "none" sentinel in the reference columns (75 of 75 `roster.weapon_uid`, 28 of 30 `ds_offer.ship_id`). `player.party_id = 1` points at a `party_set` row that doesn't exist until the party screen saves a set (dangling in 4 of the 5 states). Nothing removes a sold weapon from `party_member.weapon_uid`.
- `INSERT OR REPLACE` is used on parent tables. Once foreign keys are on, that would cascade-delete children (checked, section 2 F15).
- 64 positional `insert into T values (...)` without a column list, in the server, its tests and 3 session scripts. They break on any column change.
- `tests/diff`'s state comparison masks two non-time columns as times (`login_bonus.day`, `ds_area.last_play`) and skips `meta`, where 7 Player fields live.

**The steps** (sections 4 and 5): S0 hygiene (no schema change) → S1 one schema module + `user_version` migrations (baseline = today, verbatim) and a committed v0 fixture → S2 drop the dead columns and tables → S3 meta keys → typed columns → S4 the roster merge (+FKs) → S5 items and gear FKs → S6 the party merge → S7 play → S8 presents → S9 time and boolean conventions → S10 the module tables' keys and FKs → S11 `foreign_key_check` gates everywhere. Each step is its own commit (or a few), gated as in section 5.

## 1. Inventory

Generated by `tools/schema_inventory.py`: no hand-typed rows. Regenerate with:

```sh
tools/schema_inventory.py --state emu=E --state restore=R --state party=P --state growth=G --state deepspace=D \
    --update server/PLAN-schema.md
```

How it works (details in the script's docstring):

- It reads every C++ string literal in `server/{src,net,include,app,tests}`, joining adjacent literals and splicing run-time column names (`"update roster set " + col + " = ?"`, resolved from `col`'s assignment).
- It parses the `create table` statements and classifies every other statement as a write (insert / replace / update / delete) or a read (select / join, sub-selects included).
- A `select *` counts as reading only the columns the same file names in a `Row` accessor (`r.i("col")`, prefixes like `"add_" + k` included).
- Statements are attributed to the enclosing function or registration (`Api g_x({"Method"})`); statements inside `NATIVE_TEST` bodies and `server/tests` are counted as tests.
- The key-value keys come from the SQL literals and the helper calls (`meta` / `set_meta` / `next_uid` in server.cpp, `meta(c, ..)` in api_sphere211.cpp, `count` / `counter` in ext.cpp).
- `server/src/gacha_pools.cpp` is excluded: its `meta` is the pools DB's own table.
- Because read/write sets are an over-approximation (a column name shared by two tables of one statement counts for both), **a column flagged never-read or never-written is never named at all**.

### F7. Tables created lazily by modules: ordering

- The core creates 24 tables in `Server::schema()` (server.cpp:407-447), plus `favor` through a direct call, `favor::schema(st.h)` (favor.cpp:190).
- The modules register 32 more with `ext::Schema` (ext.h:106) and `ext::ensure_schema` runs them. That runs from 13 places, on the first use of a hook: ext.cpp:128, 132, 190, 207 and server.cpp:786, 1526, 1739, 1978, 2689, 2974, 2982, 3025, 3333.
- `wire_device` is created inside `map_device` on every soa-server login (server/net/game.cpp:182).

The consequences:

1. **Readers check for tables first.** Code that reads a module table checks `sqlite_master` first, 8 times: server.cpp:626, 687, 913; api_bonus.cpp:167, 177, 189; api_sphere211.cpp:579, 1191. Otherwise a request served before the module's first hook would fail with "no such table".
2. **Table sets differ by route.** The in-process route never has `wire_device` (1.1: "absent" in `restore`), and `tests/diff` has to skip that table.
3. **No ALTER ever happens,** so a column added to an existing `create table if not exists` silently never reaches an existing state file. Hence the `_ext` tables (F3).
4. **The modules' DDL is spread over 17 files.** Nothing shows the whole schema in one place; this plan's inventory is the first listing.

SQLite does **not** validate a `REFERENCES` parent when a table is created, so lazy creation wouldn't *fail* with FKs. The case for one place is maintainability and migration ordering: a migration step must see every table, and a fresh DB and an upgraded one must come out identical.

### F9. Statements that a schema change breaks

- **Positional inserts** (`insert [or replace] into T values (…)` without a column list): 64 in the server and its tests (`grep -rnoE "into [a-z_0-9]+ values" server/src server/net server/tests`). They are concentrated in `meta` (15), `stock` (7) and `party` (4). - **`INSERT OR REPLACE` on a parent row is a delete plus an insert.** With `PRAGMA foreign_keys = ON` the delete runs the children's `ON DELETE` actions. Checked with Python's sqlite3 3.45.1 (the same version as vcpkg's): with `ch.id references p(id) on delete cascade`, `insert or replace into p values (1, 'b')` over an existing `p` row 1 leaves `ch` empty. Today's REPLACEs on future parents:
  - `player` (server.cpp:469 seed, :1038 CreatePlayer): would null `wire_device.player_id`;
  - `roster` (server.cpp:486 seed, :1049 CreatePlayer);
  - `party` / `party_set` / `party_member` (server.cpp:501, 1053, 1142, 1188, 1196-1197);
  - `ds_area` (api_deepspace.cpp:1093, 1094, 1169): would cascade to `ds_offer` / `ds_ship`;
  - `wboss` (api_worldboss.cpp:151 `save`): would cascade to `wboss_clear`;
  - `presents` (via `present_texts`);
  - `favor`, `stock`, `subscription` (no children).

  All of them must become UPSERTs (`insert … on conflict(pk) do update set …`) before the FKs on those parents are switched on.
- **Readers of the columns**, which must change in lockstep (1.5):
  - `tools/server_state.py` (prints `roster.favor`, `party`; used by 11 session scripts and `tests/diff/diffdrive/targets.py`);
  - `tools/compare_tutorial.py`;
  - `tests/diff/diffdrive/state.py` (every table: `SKIP_TABLES`, the `TIME_COL` regexp);
  - the session scripts' own SQL: party_session.sh (`party`, `roster`, `player`), restore_favor_session.sh (`favor`, `roster`, `player`), deepspace_session.sh (`ds_*`, `player`, `presents`), growth_session.sh (`items`, `gear_items`, `stock`), sphere211_session.sh and sphere211_continue_session.sh (`sphere*`, `stock`), tower_session.sh (`mission`), restore_missions.sh (`update player`), nier_demo.sh (`roster`).
- **Who opens the state DB.** The only read-write opens of the state are `Db::open` (server.cpp:131) via `Server::open_state` (server.cpp:395-406), and the scratch servers of the selftests through the same function. soa-server's wire layer reaches the same handle (`ext::with_live_server`, server/net/game.cpp:84); the in-process route too (port/src/main.cpp:404 only picks the path). So `PRAGMA foreign_keys = ON` goes in one place (S1), and the scripts' writes are covered by the `foreign_key_check` at the end of each session (S11), not by enforcement.

- **One place.** The whole state schema lives in `server/src/state/`:
  - `schema.cpp` holds the migrations, an ordered `std::vector<Step>` of DDL plus optional C++ data mappings, and nothing else;
  - `state.h` has `int open_and_migrate(sqlite3*)`, `kSchemaVersion`, the consistency check, and the helpers `meta()` / `set_meta()` / `next_uid()` moved from server.cpp;
  - `README.md` describes the tables (the SQL below, kept current).

  `ext::Schema`, `favor::schema`, the `create table` in `map_device`, all `ext::ensure_schema` call sites and the 8 `sqlite_master` checks are removed. Modules own their *rules*, not their tables; a module that needs a new column adds a migration step there.
- **One path.** A fresh DB runs every step from version 0, so a new state and an upgraded one are the same by construction (tested: S1).
- **`STRICT` tables** (SQLite ≥ 3.37; vcpkg, Python and the CLI are all 3.45.1 here). Types are INTEGER (ids, uids, counts, booleans, times, u64 bit words as their int64 bits), TEXT (names, labels) and REAL (`ds_bonus.value` only). A STRICT table refuses a wrong type instead of storing it, which would have caught `view_status` as text.
- **Names.** snake_case. Owned objects are keyed `uid`, references to them are `<role>_uid`, and master references keep their current names (`role_id`, `master_item_id`, `gacha_id`, …). Booleans keep their names. A `day` key is `*_day` = the epoch second its reset day starts; a counter is `day_index`. Tables aren't renamed for style (F5).
- **Times** are INTEGER unix seconds on the server clock, named `*_at`. **NULL = never.** Responses format them with `fmt_time` at the boundary (as `favor_bonus_received_at` already does, api_daily.cpp:201).
- **"None" is NULL**, never 0, for every reference column. That makes `ON DELETE SET NULL` and `foreign_key_check` meaningful. The response code maps NULL to the client's 0 at the boundary: `Row::i` already returns 0 for NULL (ext.cpp `Row::i` via `sqlite3_value_int64`).
- **Booleans** are `integer not null default 0 check (x in (0, 1))`.
- **Foreign keys.**
  - Every reference between state tables is declared, `deferrable initially deferred` where rows are created in one transaction in either order (player ↔ roster ↔ party at seed / CreatePlayer).
  - Actions: `CASCADE` for parts of the parent (extensions, children of a set, attached gear), `SET NULL` for "points at" references (equipment, home, assist, support), `RESTRICT` where deleting the parent must be a decision (none today: the roster is never deleted).
  - References into the master DB aren't declared. They're checked by `state::check(master)` (S0).
- **Every write names its columns**, and parents are written with UPSERT, never REPLACE (F9).
- **One player per DB** (as today: `player` has one row; no `player_id` columns). Multi-player is out of scope (section 6).

## 4. Migration

### 4.1 Mechanism

The schema version is `PRAGMA user_version` (0 in every existing file: nothing sets it). `state::open_and_migrate(db)` replaces `Server::schema()` and all `ensure_schema` calls, and runs once in `open_state` right after `sqlite3_open_v2`:

```
v = pragma user_version
if v > kSchemaVersion: refuse to open (LOGE "state DB is newer than this build"); don't touch it
if v < kSchemaVersion and the file has a player: copy it first (sqlite3_backup) to server.sqlite3.bak-v<v>
pragma foreign_keys = off            -- outside any transaction (a no-op inside one)
for step in steps[v+1 .. kSchemaVersion]:
    begin immediate
    step.sql; step.fn(db)            -- DDL + data mapping
    pragma foreign_key_check  -> any row: rollback, LOGE the violations, refuse to open
    pragma user_version = step.n
    commit
pragma foreign_keys = on             -- every connection, every open, before the first request's "begin"
state::check(db, master) -> master references (LOGW per dangling id; not fatal: a master can change)
```

- **Step 1 is the baseline.** It's today's 58 `create table if not exists` statements, verbatim, `wire_device` included, so it's idempotent on a legacy file. It also adds any column a legacy file lacks (`pragma table_info` vs the baseline, `alter table add column` with the baseline's default): a state from before a module column was added (the `create if not exists` problem, F7) is repaired, not left to crash.
- **A fresh DB** starts at 0 and runs every step, so it's identical to an upgraded one (the S1 test).
- **Each step is its own transaction.** A failure leaves the file at the last good version, plus the `.bak`.
- **Table rebuilds** (adding FKs, `STRICT`, renames and merges) follow SQLite's 12-step procedure (sqlite.org/lang_altertable.html "Making Other Kinds Of Table Schema Changes"):
  1. `create table new_X (…)`;
  2. `insert into new_X (cols) select …mapping… from X`;
  3. `drop table X`;
  4. `alter table new_X rename to X`;
  5. recreate X's indexes;
  6. `pragma foreign_key_check`.

  It runs with foreign keys off, and the *old* table is dropped, never renamed. Since SQLite 3.26, `alter table … rename` rewrites the children's `REFERENCES` clauses whatever `foreign_keys` says. Renaming the old X away first ("rename X to old_X; create X") would repoint every child at `old_X` and break them when it's dropped. Creating `new_X` and renaming *it* to X leaves the children's `REFERENCES X` resolving to the new table. `drop column` (3.35+) is used where nothing references the column (`roster.favor` in S2, if S2 lands before the S4 rebuild).
- **The mapping conventions:**
  - **0 sentinel → NULL:** `nullif(col, 0)`.
  - **Dangling reference → the declared action.** For `SET NULL`, it becomes NULL. For `CASCADE` children (orphan `roster_ext`, `gear_items` on a missing item, `box_slots` without `box_state`), the row is dropped. Each step logs the count per relationship (`LOGW "migrate vN: party_member.weapon_uid: 2 dangling -> NULL"`).
  - **Text → typed:** `view_status`: `cast(value as integer)` does **not** work for values ≥ 2^63 (it saturates). It's converted in C++ (`strtoull` → `(int64_t)`). `event_drop_at`: `'' → NULL`, a time string → `parse_time`.

**Risks:**

- **Lockstep consumers.** `tools/server_state.py`, `tests/diff/diffdrive/state.py`, `tools/compare_tutorial.py` and the session scripts' SQL (1.5, F9) change in the same commit as the schema they read. G4's before/after diff of `server_state.py` output is how a missed consumer shows up. A script that writes a dropped column fails loudly (no such column). One that *reads* a renamed column fails loudly too. The silent risk is `state.py`, which compares whatever tables exist: a merged table makes both sides change together, so it can't hide a difference, but a masked column (S9) can.
- **The `.bak` files.** Users' saved states upgrade in place. Each step backs up first, and a newer file is refused rather than downgraded. **There is no down-migration:** going back to an older binary means restoring a `.bak`. Document this in server/README.md.
- **Deferred FKs and the request transaction.** `handle_request` wraps each request in `begin` … `commit` (server.cpp:2895). Deferred violations surface at `commit`, so a failing commit must be logged and answered as an error (and rolled back), never ignored. The S1 code checks `sqlite3_exec`'s result of `commit`. `Db::exec` and `Sql::exec` log but don't return errors today.
- **REPLACE sites missed in S0** would silently cascade once a parent's FK lands. `schema-fk-actions` plus G9 after each session catches the visible ones. A grep gate in the S0 commit (`grep -rn "insert or replace into \(player\|roster\|party_set\|items\|ds_area\|ds_ship\|wboss\|box_state\|presents\)" server/` must be empty) keeps it that way. **As built:** `tools/schema_inventory.py --lint` (S0c), on the joined literals and the scripts, with every 3.2 parent and F9's list; run it with the cheap gates.
- **`view_status` bit patterns.** Any path that formats the int64 with `%lld` or `std::to_string(int64)` would send −1. The Player response must use `(u64)`. Covered by S3's test (all-ones in, all-ones out on the wire).

## 6. Out of scope / later

- **Multi-player states** (a `player_id` on every table; soa-server serving several devices with different players). The schema keeps the one-player-per-file model; `wire_device` is the only multi-device table.
- **Renaming tables for style** (`items` → `item`, `gear_items` → `gear`, …): churn in every consumer for no behaviour.
- **Normalizing `presents.content_type` / `content_id`** into typed references: polymorphic by design (the client's content types); checked by `state::check` per type, not by FKs.
- **Moving the master-reference checks into SQLite** (e.g. copying master ids into the state): the master changes per version; a check is enough.
- **The rules gaps the inventory surfaced:** `sphere.revive_count` never incremented, the `accessory_boost` / `weapon_boost` counters never counted (a false positive: R16 found ItemCompose's ternary key, see F1), and `Item::equipped` ignoring party sets (fixed as a side effect in S5/S6). They're reported to the owners of those modules. The schema steps don't change game rules, except where an FK action *is* the rule already applied by hand (api_gear.cpp:74).
- **`event_rank_score.roles` and `counters` key patterns** (`evolution_to_<rarity>`, `add_status_<k>`): fine as they are.
- **Performance indexes:** none needed at this scale (F6). Revisit only if a profile shows state queries.
